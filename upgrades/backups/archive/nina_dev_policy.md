# NINA Development Policy

Version: 1.0
Applies to: all code, config, deploy, patch, and maintenance work in NINA

## Purpose

This policy exists to keep NINA stable, recoverable, and understandable.
A change is not considered complete just because the code was edited.
A change is complete only when it is identified, verified, recoverable, and logged.

---

## Rule 1 — Every change must have an ID

Every meaningful change must have a tracking ID before editing begins.

Allowed examples:
- R-76 for bug fix
- F-01 for feature
- S-01 for security improvement
- D-01 for debt cleanup

The ID must appear in:
- the working note for the session
- the update log
- the problem log, if it fixes a problem

No anonymous fixes.

---

## Rule 2 — One purpose per patch

Each patch must have one primary purpose only.

Good:
- Fix Telegram None handling
- Add guardian warning classification
- Improve router timeout fallback

Bad:
- Fix Telegram + rewrite memory + refactor logging + change prompts

If multiple unrelated issues are discovered, split them into separate IDs.

---

## Rule 3 — Guardian runs before and after risky work

Guardian is mandatory:
- before deploy
- after touching `core/`, `tools/`, `interfaces/`, `main.py`, `.env`, or service files
- after any patch generated by AI
- before declaring a fix done

If guardian does not pass, the change is not done.

If guardian shows warnings, they must be explicitly classified as:
- ACCEPTED NOW
- FIX NEXT
- BLOCK RELEASE

No silent warning debt.

---

## Rule 4 — Every risky change must be recoverable

Before risky edits, there must be a rollback path.

Accepted rollback methods:
- guardian auto-backup snapshot
- markdown export
- git commit, if git is enabled
- manual backup copy for one-off dangerous edits

Never perform destructive edits without recovery.

---

## Rule 5 — Runtime proof is required

A code fix is not complete until one real behavior is verified.

Accepted proof examples:
- `nina.service` restarted and stayed active
- Telegram polling confirmed
- APScheduler started
- command returned expected reply
- target bug no longer reproduced

Compile-only success is not enough.
Static-only success is not enough.

---

## Rule 6 — Logs must be updated the same day

Every completed change must update documentation on the same day.

`nina_update_log.md` must record:
- what changed
- which files changed
- brief verification

`nina_problem_log.md` or `nina_problem_log-2.md` must record:
- issue ID
- cause
- fix
- affected file
- impact, if important

If it is not logged, it did not happen.

---

## Rule 7 — Production fixes beat cleanup

When choosing between active breakage and code cleanliness:
1. security
2. startup failure
3. service crash
4. broken user path
5. bad deploy behavior
6. cleanup and type debt

This means mypy warnings, refactors, and style improvements are lower priority than real runtime failures unless they are about to cause one.

---

## Rule 8 — No blind AI patching

AI-generated code or command blocks must not be trusted blindly.

Before applying:
- read the target files
- confirm file paths are real
- confirm names match current code
- confirm the patch solves the stated issue

After applying:
- run guardian
- verify one real behavior
- log the result

AI is an assistant, not authority.

---

## Rule 9 — Protect interfaces and secrets first

Any change touching these areas is automatically high-risk:
- `interfaces/telegram_interface.py`
- `.env`
- API keys
- router/provider selection
- deploy/restart logic
- shell execution
- browser/network access
- upgrade pipeline

For high-risk files:
- do not batch unrelated edits
- verify with guardian immediately
- record verification explicitly in logs

---

## Rule 10 — Warnings must be managed, not ignored

Warnings are allowed only if they are named and tracked.

Every warning must be one of:
- temporary accepted warning
- scheduled cleanup item
- false positive
- release blocker

Examples:
- `TELEGRAMCHATID missing` → accepted warning or fix-next
- mypy advisory errors → scheduled debt cleanup
- optional service not configured → accepted warning

Warnings that stay unclassified across sessions are process failure.

---

## Rule 11 — Small changes win

Prefer the smallest safe patch that fixes the real issue.

Prefer:
- one-line variable correction
- one guard clause
- one import fix
- one policy improvement

Avoid large rewrites unless the current design is clearly failing.

NINA improves best through controlled, verified increments.

---

## Rule 12 — “Done” has a fixed meaning

A task is DONE only if all are true:
- it has an ID
- the patch has one clear purpose
- guardian was run
- runtime behavior was checked
- rollback exists
- logs were updated

If even one is missing, the task is not done.

---

## Daily operating routine

For each development session:

1. Write the issue ID and one-sentence target.
2. Edit only the files needed for that target.
3. Run guardian.
4. Verify one real behavior.
5. Update both logs.
6. Stop or move to a new ID.

Do not stack unfinished fixes.

---

## Release rule

A release/deploy is allowed only when:
- guardian passes
- no unclassified warnings remain
- rollback snapshot exists
- the day’s changes are logged

If any of these are missing, do not deploy.

---

## Default principle

Never trust memory.
Never trust assumptions.
Trust checks, rollback, and logs.
